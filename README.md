# Madori AI / イラスト間取りAI

FastAPI MVP for turning Japanese apartment floorplans into furnished real-estate style illustrations.

## Semantic Vision Provider

Semantic analysis uses `VISION_PROVIDER=openai` only. The staged flow keeps the same endpoints and artifact names:

- `artifacts/floorplan_analysis.json`
- `artifacts/floorplan_analysis_raw.json`
- `artifacts/interior_analysis.json`
- `artifacts/interior_analysis_raw.json`

OpenAI analysis uses `OPENAI_ANALYSIS_MODEL`, defaulting to `gpt-4.1-mini`. It is for semantic understanding only: room types, labels, rough locations, furniture/object signals, style/color cues, and arrangement hints. Any bbox or geometry returned by OpenAI is treated as approximate semantic guidance, not CAD-accurate structure.

OpenAI image generation remains separate and continues to use `OPENAI_IMAGE_MODEL` plus the image-generation guard settings.

## Active Providers

Semantic analysis:
- OpenAI only

Image generation:
- OpenAI only

Output hosting:
- Cloudinary optional, storage-only

Removed from the active flow:
- older third-party image providers
- Gemini analysis
- OCR
- legacy `/api/generate`

Useful config:

```text
VISION_PROVIDER=openai
OPENAI_ANALYSIS_MODEL=gpt-4.1-mini
OPENAI_ANALYSIS_TIMEOUT_SECONDS=90
OPENAI_ANALYSIS_MAX_OUTPUT_TOKENS=4096
OPENAI_API_KEY=...
```

Gemini is deprecated in this project and is not part of the active flow.

## Phase 7 Output Workflow

Phase 7 uses the staged runs flow only:

`Draft -> Visual QA -> Finalize Output`

- The frontend uses staged `/api/runs` endpoints only.
- `POST /api/runs/{run_id}/visual-qa` records manual review.
- `POST /api/runs/{run_id}/finalize-output` creates the local final output image.
- When Cloudinary is enabled, the finalized frontend view should prefer the returned hosted final URL.
- Local `/storage/...` URLs remain the fallback for preview and debugging.

## Phase 8 QA Feedback and Regeneration

QA Feedback -> Regenerate with Feedback

- regeneration outputs are versioned
- original draft/final outputs are not overwritten
- Cloudinary regenerated URL is preferred for deployed frontend
- local `/storage` URL remains fallback
- staged `/api/runs` only
- OpenAI remains the only generation provider
- Cloudinary is storage/hosting only

## Phase 1 Upload Runs

Phase 1 provides a backend-only upload workspace. It does not call AI, does not run OCR, does not generate images, and does not render watercolor output.

### Create Run

```bash
curl.exe -X POST "http://127.0.0.1:8000/api/runs" ^
  -F "floorplan=@inputs/madori.jpg" ^
  -F "interior_photos=@inputs/interior_1.jpg" ^
  -F "interior_photos=@inputs/interior_2.jpg" ^
  -F "ideal_style_reference=@inputs/sample_ai_ideal.png" ^
  -F "acceptable_style_reference=@inputs/sample_ai_ok.png" ^
  -F "ng_style_reference=@inputs/sample_ai_ng.png"
```

`floorplan` is required. `interior_photos` is optional and may contain multiple image files. Style references are optional and are grouped in metadata as:

- `style_references.ideal`
- `style_references.acceptable`
- `style_references.ng`

Named upload fields are:

- `ideal_style_reference`
- `acceptable_style_reference`
- `ng_style_reference`

Repeated `style_reference_images` are accepted for backwards-compatible generic uploads and are stored under `style_references.acceptable`.

Uploaded files are saved under:

```text
storage/runs/{run_id}/source/floorplan/floorplan.*
storage/runs/{run_id}/source/interior_photos/interior_001.*
storage/runs/{run_id}/source/style_references/ideal/style_reference_ideal_001.*
storage/runs/{run_id}/source/style_references/acceptable/style_reference_acceptable_001.*
storage/runs/{run_id}/source/style_references/ng/style_reference_ng_001.*
storage/runs/{run_id}/artifacts/
storage/runs/{run_id}/outputs/
storage/runs/{run_id}/run_metadata.json
```

The metadata includes:

- `schema_version`
- `phase`
- `run_status`
- `workspace` paths
- `inputs.floorplan`
- `inputs.interior_photos`
- `inputs.style_references`
- `processing` flags, all false in Phase 1
- `requirements` for later phases, including English labels and 1200x1200 final output

For backwards compatibility, the response also keeps top-level `floorplan`, `interior_photos`, and grouped `style_references`.

Every uploaded file entry contains:

- `original_filename`
- `stored_filename`
- `mime_type`
- `size_bytes`
- `relative_path`
- `preview_url`

Legacy aliases `filename` and `content_type` are still included for older callers.

The response returns browser-openable `preview_url` values such as:

```text
/storage/runs/{run_id}/source/floorplan/floorplan.jpg
```

### Phase 1 Validation

The upload API validates:

- missing `floorplan`
- unsupported MIME types
- files larger than 20MB
- empty uploaded files
- unsafe/path-traversal filenames

Stored filenames are generated by the backend and never use user-provided paths.

### Read Run Metadata

```bash
curl.exe "http://127.0.0.1:8000/api/runs/{run_id}/metadata"
```

No database is used in Phase 1. `run_metadata.json` is the source of truth for uploaded source files.

## Phase 5C.1 - Image Generation Draft

Purpose:

- This phase may call OpenAI Image API.
- It is disabled by default.
- It requires:
  - `ENABLE_OPENAI_IMAGE_GENERATION=true`
  - `OPENAI_IMAGE_DRY_RUN=false`
  - `confirm_generation=true`
  - `OPENAI_API_KEY`
- For this project, prompt-only draft generation is disabled.
- `use_reference_images=true` must select a local `structure_reference` image, and that structure image must be sent to the provider.
- Phase 5C.1 uses an OpenAI image-input edit request and uploads `normalized_floorplan.png` as the required `structure_reference`.
- If the current provider helper cannot actually send reference image inputs, `/generate-image-draft` fails with `400` or `501` and does not create `image_generation_draft.json`, `generated_draft_raw.png`, or `outputs/{run_id}_draft.png`.
- It creates:
  - `image_generation_draft.json`
  - `generated_draft_raw.png`
  - `outputs/{run_id}_draft.png`
- It postprocesses provider output to `1200x1200`.
- It still requires visual QA.

Example env:

```env
ENABLE_OPENAI_IMAGE_GENERATION=false
OPENAI_IMAGE_DRY_RUN=true
OPENAI_IMAGE_MODEL=gpt-image-1
OPENAI_IMAGE_PROVIDER_SIZE=1024x1024
OPENAI_IMAGE_FINAL_OUTPUT_SIZE=1200x1200
OPENAI_IMAGE_MAX_IMAGES=1
OPENAI_IMAGE_OUTPUT_FORMAT=png
OPENAI_IMAGE_QUALITY=auto
```

## Phase 6A - Structure-Locked Composite Renderer

Phase 6A adds a deterministic renderer that does not call any AI provider.

- It uses existing preprocessing/layout artifacts only:
  - `normalized_floorplan.png`
  - `binary_mask.png`
  - `edges.png`
  - `line_preview.png`
  - `layout_furniture_validated.json`
  - `render_plan.json`
- It creates a watercolor-style composite with:
  - watercolor paper background
  - room floor-tone washes by validated room bbox
  - Japanese label suppression/cover
  - English labels
  - furniture drawn by validated bbox
  - structure lines overlaid at the end from preprocessing artifacts
- It exports:
  - `storage/runs/{run_id}/artifacts/structure_locked_composite.json`
  - `storage/runs/{run_id}/outputs/{run_id}_structure_locked_composite.png`
- Output size is always `1200x1200`.

- Floorplan analysis may now include `approx_bbox` for rooms and structure objects.

## Current Strategy

- Upload a Japanese apartment floorplan and optional interior references.
- The app creates a staged run under `/api/runs/{run_id}`.
- OpenAI handles semantic floorplan analysis and interior analysis.
- Deterministic services validate, assign room functions, create layout objects, plan furniture, and build prompt artifacts.
- OpenAI image draft generation uses the staged run artifacts and the normalized floorplan reference.
- `generated_draft_raw.png` and the final output image are run artifacts, while earlier debug overlays are treated as internal diagnostics only.

Furniture planning and prompt generation are driven by staged run artifacts, not the legacy one-shot generation path.

## Deployment Notes

### Vercel / Serverless Runtime

Vercel serverless functions cannot write to the project directory at runtime. When the app detects Vercel with `VERCEL=1` or `VERCEL_ENV` set, it writes runtime files under:

```text
/tmp/madori-ai/uploads
/tmp/madori-ai/runs
/tmp/madori-ai/outputs
```

When simulating Vercel locally on Windows, the app uses the OS temp directory equivalent, for example `%TEMP%\madori-ai`.

The `/runs` static mount points to the configured runtime `runs_dir`, so generated files can still be opened during the same warm serverless runtime:

```text
/runs/{run_id}/output.png
```

Important limitation: `/tmp` is temporary and not persistent. Run files may disappear when the serverless instance is recycled. For real production persistence, upload final outputs to Cloudinary/S3/R2 and store run metadata in a database.

